# 1.3.5 Identify Input Purpose

## Learning objectives

Determine when a field's purpose must be programmatically identified, use appropriate HTML autocomplete tokens, and distinguish a field's purpose from its visible label. WCAG 2.2 criterion 1.3.5 is Level AA. It applies to fields collecting information about the user when the purpose is listed in WCAG's input purposes and the technology supports identifying it. Read the [criterion and input purposes](https://www.w3.org/TR/WCAG22/#identify-input-purpose).

## Help software recognize familiar information

A visible label tells a person what to enter, but a label such as “Your name” does not by itself supply the standardized machine-readable purpose needed by this criterion. When appropriate, HTML `autocomplete` tokens identify fields such as the user's name, email, or postal code. Browsers and assistive technologies can use these signals to offer autofill or other support. The user remains in control of whether to use such features.

```html
<label for="email">Email address</label>
<input id="email" name="email" type="email" autocomplete="email">
<label for="postcode">Postal code</label>
<input id="postcode" name="postcode" autocomplete="postal-code">
```

Choose tokens that accurately describe the information requested. An email field for a different person is not automatically covered merely because its data type is email; assess whether it collects information about the user and whether a listed purpose applies. Not every form field has a listed purpose. An arbitrary order number should not be given an unrelated token to force coverage. Labels and instructions remain necessary; autocomplete is not a replacement for them.

Inspect the rendered fields and test browser autofill where available. Support varies across browsers and settings, so also check the markup itself. For address and payment groupings, follow the HTML autocomplete syntax and use distinct sections or shipping and billing qualifiers when appropriate.

## Determine applicability before selecting tokens

Start with the person whose data is being collected. A profile form asking for the current user's name, email address, telephone number and postal address may include several listed purposes. An order form asking for a friend's name requires a closer scope analysis; the criterion concerns information about the user. Also check whether the requested purpose appears in WCAG's list and whether the markup technology can identify the expected meaning. Not every field, such as an order reference, has a corresponding listed purpose.

A label and an autocomplete token have different jobs. “Email address” is a human-readable label and gives the control a name when correctly associated. autocomplete="email" identifies a standardized purpose for software. Both can be useful on the same input. A placeholder is not a reliable replacement for the label, and setting type="email" alone should not be treated as equivalent to identifying the listed autocomplete purpose.

## Avoid misleading autofill

Choose the token that matches the information requested. A name field can use an appropriate name token; a postal code can use postal-code. Do not apply a familiar token to an unrelated field merely to make an automated check pass. If shipping and billing addresses appear together, follow the supported HTML syntax for grouping and qualifiers so software can distinguish them. Test what actually happens when autofill is offered, and make it possible for a user to inspect or correct entered values.

Personal data and autofill settings differ among users. Avoid assuming that a browser will have a value, or that a person wishes to use autofill. The form must still be understandable and usable without autofill. Tokens expose purpose; they do not themselves validate values or provide secure storage.

## Inspect and verify

Review the WCAG input-purpose list and inventory applicable fields. Inspect each input's label, autocomplete value, and surrounding context in the browser. Try autofill using a test profile where available, then verify that values land in the intended fields. Record browser behavior and any unavailable feature; the markup remains inspectable even if a particular browser does not offer autofill.

A common error is using the same generic token for several different address fields without considering grouping. Another is assigning a token to a field whose meaning differs from the token. Review the HTML specification and the relevant WCAG guidance when selecting less familiar tokens, and test with actual combinations of controls rather than treating isolated examples as proof of full form conformance.

## Worked example: shipping information

Consider a checkout asking the buyer for their email and shipping postal code. The team adds visible labels and appropriate autocomplete values so a browser can recognize each purpose. A tester uses a sample browser profile and confirms the postal code is offered in the postal-code field rather than the email field. The user can still type or edit either value, and the form explains validation errors in text.

The checkout also asks for a coupon code. The team should not assign autocomplete="postal-code" simply because both values may be short strings. Their meanings differ, and a misleading token can insert inappropriate personal information. An input's visual shape or data type is not sufficient to decide its semantic purpose. Examine the actual question, the person the information concerns, and the list of input purposes.

If a form has separate shipping and billing address groups, verify that supported autocomplete grouping and qualifiers match the intended destination. Test the groups together rather than copying the same snippet into both without review. Browser support and saved-profile contents vary, so a missing autofill suggestion in one environment is not by itself a complete judgment. Inspect the markup and document the test environment alongside the observed behavior.

Do not confuse this criterion with error prevention or privacy guarantees. Machine-readable purpose can make entry easier, but the application must still handle submitted information appropriately and give users clear labels and instructions. Test these responsibilities separately.

## Required lesson activity

Build a profile form with the user's name, email address, postal code, and an unrelated account reference. Associate visible labels with each field, choose appropriate autocomplete tokens for applicable fields, and leave the unrelated field without a misleading token. Inspect the rendered markup, try browser autofill if available, and explain why each token was selected.

## Mini-assessment

1. Does a visible label alone supply a standardized input-purpose token?
2. Does this criterion apply to every field regardless of whose information it collects or whether the purpose is listed?
3. What is wrong with assigning `autocomplete="email"` to an order number?

**Answer guide:** 1. No; the label and machine-readable purpose serve different roles. 2. No; check the criterion's scope and technology support. 3. The token misrepresents the requested information and can cause inappropriate assistance.
